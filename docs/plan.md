## 2. 解決すべき課題と対象利用者

**対象とする単一の利用者**：日々の学びを自分の知識として定着させたいと考えている開発者自身（特定の専門・立場に限らず、講義・読書・資格勉強・独学などでインプットした内容を、やる気が出ない日でもゲーム感覚で楽しくアウトプットできるようにしたいすべての学習者を起点としている）。

**切実な不便**

- インプット偏重による「わかったつもり」の発生：講義資料や参考書、動画教材などで学んだ直後は理解した気になっても、いざテストや実践の場に立つと自分の言葉や数式・論理で再現（アウトプット）できず手が止まってしまう。
- やる気依存による学習継続の重さ：「復習や問題演習をしなければ」と頭ではわかっていても、気分が乗らない日は最初の一歩が重く、単調な解き直しや日々の学習時間記録が三日坊主で途絶えてしまう。
- デバイス間の分断と得意分野への偏り：PCで学習しながら手元のスマホで撮ったノート図解や疑問メモを整理する手間が集中を途切れさせるほか、自分が解きやすい得意分野ばかり進めて苦手分野を放置したまま試験直前を迎えてしまう。

**現在の代替手段とその限界**：現在は、時間計測にポモドーロタイマー、PC・スマホ間のメモ移動にチャットツールの自分宛て送信、知識整理に汎用ノートアプリを併用し、補助的に既存の学習記録SNS（Studyplus）や習慣化RPG（Habitica）、既成クイズアプリなどを試している。しかし、小学生向け学習タブレットのように「開くだけでキャラクターが応援してくれ、ゲーム感覚で自然に勉強が続く体験」を、全年齢の自由な学習内容で実現できるツールが存在しない。既存の大人向けアプリは「時間計測だけ」「自己申告のToDo管理だけ」「決められた既成問題を解くだけ」と機能が分断・固定化されており、自分が今日学んだ知識を素材にして、その日の気分に合わせた世界観で楽しくアウトプットし、苦手科目の偏りまで防げる統合環境になっていない点が限界である。

## 3. 中核的価値

**提供する決定的な価値**：「エネスタ（EneStu）」は、子供向け学習タブレットが持つ「開くだけでキャラクターが寄り添い、ゲーム感覚で自然に勉強が続く楽しさ」を、講義・資格・読書・独学などあらゆる学びを自由に教材化できる形へと進化させた統合型学習プラットフォームである。日々の勉強タイマー記録、PC・スマホ間のノート写真および疑問メモの即時同期、テスト前の言語化による理解度チェック、そして確認テストと誤答原因分析という一連の学習サイクルを、すべての学習資産を保持したまま「ダンジョンRPG・乙女ゲーム・探偵・ライブ・カフェ」の5つの世界線（UI・演出テーマ）をその日の気分で自由に切り替えられるゲーム体験へと統合することで、やる気が出ない日でも無理なくアウトプットを継続でき、苦手分野の偏りも防げる自律的な学習習慣を実現する。

## 4. 技術スタックの選定理由と自習計画

**フロントエンド：Next.js（App Router）＋ TypeScript ＋ Tailwind CSS**

- 公開されているコードが多く、型も効くので、エージェントが正確なコードを生成しやすい。
- 5つの世界線は「テーマ定義オブジェクト（配色・キャラ・セリフ・用語）」として型で縛り、CSS変数で切り替える。こうすれば画面のコードは1つで済む。
- スマホからも使うので、モバイルファーストのレスポンシブ設計にし、PWA化して「ホーム画面に追加」で開けるようにする。

**バックエンドおよびデータベース：Supabase（PostgreSQL / Auth / Storage / Realtime）**

- 学習記録・問題・誤答はリレーショナルな構造なので、PostgreSQLが合う。
- ノート写真の保存（Storage）、PC・スマホ間の即時同期（Realtime）、認証と行単位セキュリティ（Auth＋RLS）が1つの基盤にまとまっていて、クレジットカードなしの無償枠で使える。
- スキーマから型を自動生成できるので、DBと画面の型のずれを防げる。

**ホスティング環境：Vercel**

- Next.jsと相性が良く、GitHubにpushするだけで自動ビルド・公開まで進む。
- ブランチごとのプレビュー環境で、本番に出す前に確認できる。

**自習計画：TechTrain Railway**

- 第1～2週：React / Next.js の課題で、状態管理とコンポーネント設計を学ぶ。
- 第3週まで：DB設計・Web APIの課題で、テーブル設計とリレーションを学ぶ。

## 5. 8週間の垂直スライス開発計画

### 第1週：学習タイマーの記録と応援表示（全層開通）

**利用者シナリオ**：科目名を入力してタイマーを開始・停止すると、学習記録が保存される。今日の合計学習時間とキャラクターの応援セリフが表示され、再読み込みしても記録が残る。

**全層貫通の範囲**

- UI層：科目入力欄、開始・停止ボタン、今日の合計時間、応援キャラ表示（ダンジョン世界線1種）。
- API・DB層：学習記録テーブル（端末ID・科目・開始/終了時刻）を作成し、Route Handler経由で保存・取得する。端末IDはlocalStorageに保持する。
- インフラ層：GitHubリポジトリとVercelの自動配備を開通させ、Supabaseの接続情報を環境変数に登録する。

**完了要件**：公開URLから誰でもアクセスでき、タイマーの記録が保存されて、再読み込み後も表示されること。

### 第2週：今日の学びから確認テストを自作して解く

**利用者シナリオ**：今日学んだ内容を一問一答カードとして登録し、出題モードで解く。正誤が記録され、ダンジョン世界線の演出つきで結果が表示される。

**全層貫通の範囲**

- UI層：カード登録フォーム、出題画面、正誤結果の演出表示。
- API・DB層：問題カードテーブルと解答履歴テーブル（正誤・解答日時）を新設し、登録・出題・記録の処理をつなぐ。
- ハーネス：Vitestを導入し、正誤判定ロジックの単体テストを配備する。

**完了要件**：本番環境でカードを作成して解き、解答履歴が保存・表示されること。

### 第3週：誤答原因の記録と苦手分野の可視化

**利用者シナリオ**：間違えた問題に原因タグを付けて記録すると、科目別の正答率と学習時間の偏りが表示される。苦手科目が「今日のクエスト」として提示される。

**全層貫通の範囲**

- UI層：誤答時の原因タグ選択（知識不足／理解不足／ケアレス）、科目別の集計画面、今日のクエスト表示。
- API・DB層：解答履歴に原因カラムを追加し、科目別の正答率・学習時間を集計するクエリを実装する。
- インフラ層：テーブル変更のマイグレーションを、既存データを壊さずに本番DBへ適用する。

**完了要件**：本番環境で苦手科目が集計結果に基づいて提示されること。週末に友人2名に操作してもらい、フィードバックを記録していること。

### 第4週：利用者検証に基づく適応と世界線の切り替え

**利用者シナリオ**：第3週のフィードバックで指摘された不便が解消されている。その日の気分で5つの世界線を選ぶと、学習データはそのままに画面の配色・キャラ・セリフが切り替わり、次に開いたときも選んだ世界線が保たれている。

**全層貫通の範囲**

- 設計適応：フィードバックに応じて画面の流れや機能の優先度を見直す（ピボット枠）。
- UI層：世界線の選択画面と、テーマ定義（配色・キャラ・セリフ・用語）による画面全体の切り替え。
- API・DB層：選択中の世界線を保存する設定テーブルを追加する。
- ハーネス：5つの世界線すべてが必要な項目を定義しているかを確かめるテストを追加する。

**完了要件**：本番環境で5つの世界線を切り替えられ、指摘への対応内容を説明できること。

### 第5週：認証・権限分離と自動回帰テストの配備

**利用者シナリオ**：ログインすると自分の学習記録だけが表示され、他人のデータは見ることも変更することもできない。端末IDで保存していた過去の記録はアカウントに引き継がれる。

**全層貫通の範囲**

- UI層：ログイン・ログアウトボタンと、認証状態に応じた表示の制御。
- セキュリティ層：Supabase Authを導入し、全テーブルに行単位セキュリティ（RLS）のポリシーを適用する。端末IDのデータをユーザーIDへ移行する。
- ハーネス：GitHub Actionsで型検査・Lint・Vitestをpushごとに自動実行し、権限と集計ロジックのテストを追加する。

**完了要件**：他人のデータにアクセスできないことが、テストと本番環境の両方で確認されていること。

### 第6週：スマホからのノート・疑問メモの即時同期

**利用者シナリオ**：スマホで撮った手書きノートの写真や疑問メモを投稿すると、PCで開いている画面にリロードなしで即座に反映される。

**全層貫通の範囲**

- UI層：スマホ向けの投稿画面（カメラ撮影・メモ入力）、モバイル最適化、PWA化（ホーム画面への追加）。
- API・DB層：Supabase Storageへの画像保存と、メモテーブルの新設。
- 通信層：Supabase Realtimeで変更を受け取って画面へ即時反映し、切断時の自動再接続と接続状態の表示を行う。

**完了要件**：本番環境でスマホとPCを同時に開き、スマホからの投稿がPCへ即座に反映される様子を実演できること。

### 第7週：言語化チェックとセキュリティ総点検

**利用者シナリオ**：テスト前に用語を自分の言葉で説明すると、登録済みのキーワードがどれだけ含まれているかで理解度が判定され、足りない観点が表示される。

**全層貫通の範囲**

- UI層：説明の入力欄と、判定結果・不足キーワードの表示。
- API・DB層：用語ごとのキーワード登録と、説明文・判定結果の保存。
- 外部連携層（余力があれば）：無償枠のLLM APIによる講評を追加する。API障害時はキーワード判定だけで動き続けるようにする。
- セキュリティ総点検：環境変数の漏洩確認、RLSの適用漏れ確認、不要な公開エンドポイントの遮断。

**完了要件**：本番環境で説明文の理解度判定が動作し、セキュリティ点検の結果を説明できること。

### 第8週：実運用データを使った成果実演と総括

**実現する目標**：8週間自分で使い続け、学習データが蓄積された本番環境で、質疑応答を含めた実演を行う。

**報告内容**

- 誰のどんな課題を解決したか（やる気が出ない日でも続けられるアウトプット習慣）。
- 第3～4週の利用者フィードバックから、何をどう変えたか。
- AIエージェントとハーネス（型・テスト・CI・AGENTS.md）をどう組み合わせて、速度と品質を両立させたか。
- 今後の運用・改善の計画。

**完了要件**：蓄積データを使った本番環境の実演が、その場で問題なく動作すること。

## 6. ハーネス設計と品質管理方針

**自動テストの導入計画**

- Vitest：学習時間の集計、正答率・苦手判定、キーワード判定、テーマ定義の網羅性（全世界線が必要なキーをすべて持っているか）を単体テストする。
- Playwright：主要な流れ（タイマー記録、問題作成から解答、世界線切り替え）をE2Eテストする。
- GitHub Actions：push時に型検査（tsc --noEmit）、ESLint、テストを自動実行し、失敗したらマージしない。

**エージェント規範定義の導入計画**：リポジトリ直下に AGENTS.md を置き、次の内容を明文化する。

- 技術スタック・ディレクトリ構成・命名規約
- 禁止事項（秘密鍵の直書き、any の使用、RLSなしのテーブル作成）
- 「変更前に計画を提示する」「テストと型検査がすべて通るまで修正を繰り返す」という完了条件
- 世界線の追加手順（テーマ定義の型に従い、テストも追加する）を規範ファイルとして別に用意し、エージェントが毎回同じ手順で作業できるようにする
